# TIL — T12 다중 품목 단가표 합산(Sum) 청구 정책

## 1. 결함: `[0]` 하드코딩 — 단일 품목 전제가 다품목 스펙에 방치된 경계 결함

- 거래처 등록(화면 ②)은 `priceTable` 배열에 복수 품목을 받지만,
  월 정기 청구 엔진(`invoiceService.createInvoiceBatch`)과 청구서 프리뷰
  (`invoices.js` 일괄 모달)는 `priceTable[0]`만 읽어 공급가액을 산정했다.
- 시스템 구축 초기 단일 품목 전제로 작성된 인덱스 참조가 스펙 확장 후에도
  그대로 남은 전형적 사례. Planner 전수 스캔(`priceTable`·`[0]`)으로
  실결함 2건 vs 오탐 5건(표시 요약·초기 선택·단일 언래핑·단언문)을 분리했고,
  partners 목록 요약·ledger 초기 선택 등은 의도된 `[0]`이라 손대지 않았다.

## 2. 합산 정책: 전 행 reduce, VAT는 총액 기준 1회 절사

- 공급가액 공식(백엔드·프론트 동일식):
  `(Array.isArray(priceTable)?priceTable:[]).reduce((acc,it)=>acc+(Number(it.unitPrice)||0),0)`
- **0원 품목 포함**: 견본·무상 임가공(`unitPrice: 0`)도 정상 합산(0이 더해짐).
  빈 배열·합산 0 이하는 기존대로 skip(`skippedPartnerIds`).
- **VAT는 개별 품목별 계산 후 합산이 아니다**:
  총 공급가액 기준 `Math.trunc(supply*0.1)` 1회 절사, `Total = Supply+VAT`.
  품목별 절사 후 합산하면 원 단위 절사 오차가 누적되므로 총액 1회 원칙을 유지.
- DB 마이그레이션 불필요(`default_price_json`에 전 행 보관済),
  기존 발행분은 회계 확정 기록이라 소급 수정 안 함 — 신규 배치부터 적용.

## 3. 단가 소스 일치: 프리뷰와 백엔드는 같은 식을 쓴다

- 백엔드만 고치면 "프리뷰 금액 ≠ 실제 발행액" 불일치가 생기므로
  `invoices.js` 프리뷰에 문자 단위 동일식을 원자 적용.
  대양공업(50000+35000) 기준 프리뷰 ₩85,000 → 발행 공급가 85000·VAT 8500·
  합계 93500 일치를 Reviewer 실기동으로 실증.
- 공통 헬퍼 미추출 결정: 한 줄 식이라 중복 제거 이익보다
  renderer 클래식 스크립트의 로드 체인·R1 표면 증가 비용이 큼.
  일치는 e2e 총액 단언으로 고정한다.

## 4. 원장 불변식: 합산돼도 `Billed - Paid == running_balance`

- 청구·원장 기표가同一 트랜잭션에서 동일 supply/vat/total로 일어나고,
  `running_balance = 직전 잔액 + total` 구조라 금액이 커져도 불변식은
  수학적으로 보존된다. e2e의 `invariantBalance`가 배치 후·부분입금 후·
  완납 후·최종 전수까지 4회 대조 — T12에서도 전 구간 통과.

## 5. 회귀 방지: 단위 2건 + 통합 기대값 갱신

- 신규: (a) 50000+35000 → 85000/8500/93500 + ledger 동일 기표,
  (b) 10000+0 → 10000 합산. (b)는 구 로직에서도 우연 통과하는
  가드 케이스임을 명시 — Red 입증은 (a)와 e2e가 담당.
- e2e: EXPECTED_TOTALS 155000/15500/170500 → 190000/19000/209000.
  입금액(16500)은 고정하고 `remaining = 총액−입금` 식만 적용해
  38500→77000, 완납 77000, 대시보드 실입금 93500으로 연동.
  (Planner의 43500안은 존재하지 않는 50000원 입금 전제라 식 검증 후 정정.)
- 결과: unit 115 + e2e 1 + runtime 4 = 120 PASS.
